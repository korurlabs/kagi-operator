# kagi-operator

Kubernetes operator for [Kagi](https://kagi.pw). It delivers secrets and TLS
certificates managed in Kagi into a cluster, either as native Kubernetes
`Secret`s or — with no secret persisted at all — straight into the workloads
that need them.

## What it does

**`KagiSecret`** — resolves a Kagi app (`spec.appId`, or `spec.folderPath` as a
fallback) for an `spec.environment` and delivers its secrets one of two ways,
selected by `spec.mode`:

- `Secret` (default) — writes the fetched values into the Kubernetes `Secret`
  named by `spec.managedSecret`, keeping it in sync on every reconcile.
- `Injected` — delivers the values directly to the workloads named by
  `spec.rollout` without ever materializing a standalone `Secret`.

Optional `spec.rollout` (`deployments` and/or `workloadSelector`) restarts the
consuming workloads when the synced material changes.

**`KagiCertificate`** — the same idea for a certificate stored in Kagi
(`spec.certificateID` or `spec.folderPath`), delivered into the `Secret` named
by `spec.managedSecret`. Status surfaces `thumbprint`, `notAfter` and
`expiresInDays` so expiry is visible with `kubectl get`.

**Pod injection (secretless delivery)** — a mutating admission webhook injects
the `kagi-init` init container into pods that carry the label
`kagi.pw/inject: "true"`. The init container exchanges the pod's projected
ServiceAccount token for a short-lived Kagi token and fetches the secrets at
startup, so no long-lived credential is mounted into the workload. Per-pod
configuration travels in annotations (`kagi.pw/app-id`,
`kagi.pw/environment`, `kagi.pw/watch-version`, `kagi.pw/container`,
`kagi.pw/audience`) — but only the **label** gates opt-in, because Kubernetes
admission selectors match labels, not annotations. Unlabeled pods never reach
the webhook.

The webhook's serving certificate is issued, published, rotated and monitored
by the operator itself (`internal/certs`). There is **no cert-manager
dependency** on either install path.

## Authentication

The operator calls the Kagi API with a **Personal Access Token**. Both install
paths point it at a `Secret` holding that PAT; an individual `KagiSecret` /
`KagiCertificate` can override it per object with `spec.tokenSecret`.

Operator self-auth via Kubernetes workload-identity token exchange (no static
PAT in the cluster) is a **Phase 2** item and is not wired today. The
workload-identity path used by *injected application pods* is unrelated and is
fully implemented.

## Install

### Helm (primary path)

```sh
kubectl create namespace kagi-operator-system
kubectl create secret generic kagi-operator-token \
  -n kagi-operator-system \
  --from-literal=token=<your Kagi PAT>

helm install kagi-operator oci://ghcr.io/korurlabs/charts/kagi-operator \
  --namespace kagi-operator-system \
  --set auth.existingSecret=kagi-operator-token
```

Every knob — injection on/off, metrics, RBAC, leader election, bring-your-own
webhook TLS, CRD retention — is documented in
[`charts/kagi-operator/README.md`](charts/kagi-operator/README.md). Read that
before installing into a shared cluster; it also spells out exactly which
cluster-wide RBAC the chart grants and why.

### Raw manifests (`kubectl` only)

```sh
kubectl apply -f https://github.com/korurlabs/kagi-operator/releases/download/v<VERSION>/install.yaml

kubectl create secret generic kagi-operator-token \
  -n kagi-operator-system \
  --from-literal=KAGI_TOKEN=<your Kagi PAT>
```

The bundle installs into the namespace `kagi-operator-system` and names its
objects with a `kagi-operator-` prefix, matching the Helm defaults. The manager
is preconfigured with `--default-token-secret=kagi-operator-token` in its own
namespace, so the `Secret` above is all that is required; the key may be
`KAGI_TOKEN` or `token`. Apply order does not matter — the operator retries
until the `Secret` exists.

This path has no values to tune. Anything beyond the defaults (disabling
injection, custom images, resource limits) means using the chart.

## Development

```sh
make manifests generate   # regenerate CRDs, RBAC and DeepCopy from markers
make test                 # unit tests (envtest: real API server + etcd)
make lint-fix
make run                  # run locally against the current kubeconfig context

make docker-build docker-push IMG=<registry>/kagi-operator:<tag>
make build-installer      # re-render dist/install.yaml
```

`make build-installer` mutates `config/manager/kustomization.yaml` as a side
effect (`kustomize edit set image`) — restore that file afterwards. `dist/`
is regenerated by the release workflow; do not hand-edit it.

Releases are cut by pushing a `kagi-operator/v<VERSION>` tag, which publishes
the image, the OCI chart and the `install.yaml` release asset. Agent-facing
notes on what in this tree diverges from the kubebuilder scaffold live in
[`AGENTS.md`](AGENTS.md).
